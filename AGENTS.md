This repo is driven through Bram. The canonical worklist gate is the conventions in `.claude/bram-conventions.md`, which each agent receives through its own channel (Claude: `CLAUDE.md`; Codex: `developer_instructions` in `~/.codex/config.toml`; OpenCode: `.opencode/opencode.json`; Antigravity: `.agents/rules/`) and which each agent's Bram guard, installed by Setup, enforces at runtime. Explicit same-turn opt-out phrases such as "just do it" are recorded host-side when Bram sends the turn. Read `.claude/bram-conventions.md` for the full conventions, including opt-out phrases, the two-stage proposed → applied → committed flow, approval payload shape, lifecycle calls, and edge cases.

Quick summary so you can act in this turn:

- `<state>/` below is Bram's state folder: `.bram/` if it exists, else `resources/`.
- First response to a change request must be **(a)** a clarifying question, **(b)** a proposal — write the prose to `<state>/worklist-drafts/<id>.md` (sections `# Before` and `# After`), then add a metadata-only item to `<state>/worklist.json` with non-empty `id` and `file`/`files` (no `before` / `after` inline — the guard rejects them), or **(c)** read-only investigation explicitly prefaced *"I don't yet have enough context to propose; I need to check X first"* — and the very next action after that check must be the proposal write, not narration of a plan.
- For XMLUI questions or non-obvious markup choices, ask the XMLUI MCP server's how-to search first (`xmlui_search_howto`), then component docs (`xmlui_component_docs`) for exact props, events and methods, and only then examples, as a fallback or to confirm local style.
- File edits and shell writes on paths not covered by a proposed/applied worklist item are blocked at runtime, whatever the tool (`apply_patch`, `Write`/`Edit`, `write_file`/`edit_file`, shell redirects, `mcp__filesystem__*`). Antigravity's guard doesn't yet see an MCP tool named `mcp_<server>_<tool>`, but the rule still applies to it. Following the convention avoids hitting that wall.
- Approval comes from the Worklist tab: the user ticks one or more item rows, then clicks **Start** (or **Start & commit** / **Commit** / **Drop**) beside the message box — the button generates an `approved: {"items":[...]}` / `drop: {...}` payload. A message the user sends with items selected is feedback addressed to those items and arrives as `iterate: {...}`; with nothing selected it is general chat. These payloads are the wire format the host parses, not something the user types. When the user asks "how do I approve?" answer **"Tick the item in the Worklist tab, then click Start"**. Never instruct the user to type or paste `approved:` / `drop:` / `iterate:` payloads, and don't infer authorization from free-text replies.
- **Lifecycle calls.** Claude, OpenCode and Antigravity use loopback curl to the port in `<state>/.bram-port`, as the conventions' Transports section shows. **Codex:** use the **filesystem channel** instead — its sandbox refuses loopback connections (#130). Write `<state>/.worklist-intent.json` as `{"nonce":"<unique>","route":"<r>","body":{...}}` where `<r>` is `worklist-resolve`, `worklist-mutate`, or `worklist-commit` (body `{ "ids": [...], "message": "..." }`); then read `<state>/.worklist-result.json` and act on the entry whose `nonce` matches yours. Do **not** continue silently if the result is missing or `ok` is `false`. The filesystem channel works for every agent.
- `worklist-commit` is single-shot per approval: after a slow commit, never send it again (no fresh nonce, no second POST) — check `git log` first.
- For `approved:` turns, the gate decides the call. **Start** (apply gate): skip `resolve`, make the edits from the proposal, then `mutate` `{"op":"advance","ids":[...],"status":"applied"}`. **Start & commit**, or **Commit** on a begun `proposed` item (`gate: "apply-and-commit"`): edit if needed, then `worklist-commit` with no `advance`. **Commit** on `applied` items: `worklist-commit`. For `drop:` turns, `resolve` first, then `mutate` `{"op":"prune","ids":[...]}`.
- For `iterate:` turns, do **not** call `resolve` or `mutate`; iterate authorizes no lifecycle change, and the host sets and clears the claim itself. Read any `feedbackRef` draft from `<state>/feedback-drafts/`, and revise the proposed draft or applied files according to `.claude/bram-conventions.md`.
- For `skip-worklist:` turns (your incoming turn begins literally with `skip-worklist: `), the user has authorized a direct edit for this turn; the host has already written a fresh `direct-edit` record to `<state>/.worklist-direct-edit.json`. Do **not** propose or write a worklist item — act on the rest of the message as a direct edit, which the guard allows.
- `<state>/worklist.json` carries a top-level `version: N` integer. Any write you make must set `version: N+1` where `N` is what was on disk when you read the file. The guard denies stale writes with `reason=stale-worklist-version`; re-read, rebase, retry. `mutate` bumps the version on its own path. A missing version field counts as 0.
